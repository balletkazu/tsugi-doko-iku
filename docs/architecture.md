# アーキテクチャと開発計画

## 既存コードの調査

`main` の `f4b80d2` 時点では4件の単体 HTML で構成されていた。`index.html` は6地点の発見、行きたい場所、栞、日記を実装。`index-1.html` は写真と栞の装飾を追加したが、引用符由来の構文エラーがあった。`index-2.html` はその修正版。`travel-v03.html` は地図、移動条件、Google マップへの導線を追加していた。各版は `localStorage` を使い、独自の時刻表・運賃検索や利用者間同期は実装されていなかった。

新しい試遊版も、発見、行きたい場所、栞、日記、地図の導線を引き継ぐ。過去の4ファイルは参照用として GitHub に残す。試作の保存キーは共通で値が版間で変わり得るため、新版は独立したデータベースを使用する。既存利用者のデータを新環境へ引き継ぐ時点で、サンプルデータを用意して明示的にインポートできる仕組みを検証する。

## フェーズ1 試遊版

- `public/index.html` と `style.css` がアプリ外枠、`app.js` が画面・操作、`ui.js` と `records.js` が表示とフォーム、`core.js` が検索や座標計算、`data.js` が編集データ、`storage.js` が端末内の記録と画像処理を担当する。
- ハッシュルーティングと静的配信を採用し、サービス側の環境変数と外部 JavaScript 依存をゼロにする。Vercel は `npm run build` で `dist/` を生成する。Manifest とサービスワーカーでホーム画面への追加とアプリ外枠のオフライン利用を準備した。Google マップや公式サイトを開く際には接続が必要。
- 厳選9地点をテーマ・検索語・任意の旅人タイプで閲覧する。ホームは編集部のサンプル投稿6件を、みんなの旅・フォロー中・写真・旅の日記・旅の栞に分けて表示する。フォロー・反応・保存は端末内。写真は出典と再利用条件を確認した実写を用いる。[写真の利用条件](photo-credits.md)
- 富山市の対象路線では路面電車、バス、徒歩を組み合わせ、時刻表と徒歩上限を使ってアプリ内で経路を検索する。対象外の地域は希望条件のメモと Google マップへの導線を提供する。寄り道はユーザーが選んだ地点、または許可した現在地から掲載スポットの直線距離を計算する。経路に沿った判定と時刻・運賃の取得はフェーズ3。
- 栞と日記は IndexedDB に保存する。栞は印刷・PDF またはテキスト共有。日記は自分だけで、写真・場所・気持ち・本文を保存する。写真は JPEG・PNG・WebP・AVIF を最大3枚、各20MBまで取り込み、最大1440pxの JPEG に再エンコードして元の EXIF を持ち込まない。現在地は操作時にだけ要求し、ブラウザー内のその場の計算に使用する。
- スタンプは `国 / コレクション / 項目` の識別子で端末内に保存する。都道府県は全47件を収録。他の4区分は一部を掲載し、件数は掲載分の分母を表示する。スタンプ帳を実装し、地図と表彰は公式目録を揃える段階で追加する。

## フェーズ2 旅人同士の共有と安全管理

アカウント、フォロー、コメント、ハッシュタグ、横断検索、写真の掲載許諾を含む実装順と受け入れ条件は [コミュニティ計画](community-roadmap.md) に記録する。

認証、管理された PostgreSQL、オブジェクトストレージを候補にする。ユーザー／プロフィール、旅先、栞、日記、写真、投稿、反応、訪問、ブロック、ミュート、通報を別のリソースとして設計する。`Place(countryCode, placeId, labels, geometry, source, license, verifiedAt)` を地名の基準にし、訪問は安定したコードを参照する。

公開範囲は `private / restricted / public` を基本とし、限定公開は閲覧を許可したアカウントを保持する。最初からすべての記録と画像を非公開にし、サーバー側ですべての読み書きに所有者・閲覧者・ブロック関係を適用する。限定コンテンツのサムネイルにも同じ制約を適用する。削除・公開範囲の縮小が即時反映されるよう、非公開画像の署名付き URL は短寿命にする。画像のメタデータ削除・容量検証はサーバーでも行い、本人が持つ共有権限を確認する。

読む側にブロック・ミュート、投稿者に公開範囲変更と削除、運営側に通報キュー、対応履歴、再審査フローを用意する。反応は投稿者に意味が伝わる種類別の通知を中心にし、公開の人気順位は設けない。レート制限、監査ログ、データ持ち出しと退会、バックアップと復元のテストまで揃えて招待試行へ進む。

## フェーズ3 交通・寄り道・地理データ

国内の乗換案内 API を含む比較、費用、規約、徒歩上限の扱いは [乗換検索の検討](transit-evaluation.md) に記録する。

`RouteProvider.search()` を子画面から独立させ、提供元、取得日時、適用済み条件、区間、経路形状を結果に保持する。徒歩上限を満たす候補と超える候補を区別し、データ不足時には外部リンクを出す。未確認の時刻を補完して表示することは避ける。寄り道は実際の経路形状に近い地点を選び、追加時間は計算できた場合にのみ示す。公式一覧からコレクションを拡充し、地図フィーチャーとスタンプに同じ識別子を使う。地図のない代替表示も維持する。

## フェーズ4 商用品質・配布

iOS と Android 実機でキーボード、写真選択、ネイティブ共有、インストール、オフライン復帰、読み上げを確認する。端末や通信状況を変えたパフォーマンス確認、権限テスト、運営手順、障害時の復旧、配布方法を揃える。PWA の実績を見てネイティブ展開を選ぶ。有料の高度な栞は無料導線の成立と需要を確認した後に検討する。

## 外部サービスの判断材料

| 候補 | 現時点の費用・規約の扱い | 代替 |
|---|---|---|
| Google マップ URL | 初期版は API キーなしの外部リンク。入力地名はリンクを開く時に Google に渡る。別途 Routes API を使う場合は従量課金、無料利用枠、保存や帰属表示の条件を採用前に再確認する。 | 公共交通事業者の経路案内、オープンデータを使う経路計算。 |
| GTFS・OpenTripPlanner | 地域ごとのデータ範囲と規約が前提。ソフトウェアはオープンソースでも、サーバー運営とデータ更新の費用を見積もる。 | 地域・事業者の公開時刻表、商用乗換 API。 |
| Supabase など | 共有機能の候補。無料枠を検証環境の候補とし、本番の DB・画像配信・バックアップ・メール送信を利用量別に見積もる。 | 認証と PostgreSQL、オブジェクトストレージをそれぞれ管理する。 |
| Vercel | 試遊用のプレビューを想定。契約中のチーム権限を確認し、商用公開時のプランと利用条件を改めて判断する。 | 要件に合う静的ホスト。 |
| 公式一覧・画像 | 施設、自治体、環境省、UNESCO などの一次資料で掲載名・出典・利用条件を確認する。写真は権利者の許諾または個別ライセンスを記録する。 | 掲載許諾を得た旅人の写真、撮り下ろし写真。 |
