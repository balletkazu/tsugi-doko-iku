# 独自乗換案内のデータ運用と全国への拡張

富山市では、再利用できる静的時刻表の2フィードと徒歩行列をアプリに同梱し、端末内で検索する。プレビューで使うエンジンは、停留所ごとに到着時刻と歩行秒数の両方を保持し、乗車回数を1回ずつ増やして候補を調べる。早着でも歩行時間が長い候補で、徒歩を抑えた候補を消さない。上限は秒単位で最初の徒歩、乗り換え、最後の徒歩に適用する。探索範囲は地域、収録期間、出発から6時間、乗り換え2回まで。[富山の操作例とデータの出典](toyama-pilot.md)

## 検証とAIの使い方

- 採用済みの提供元、配布URL、ライセンスと交通モードは [地域カタログ](../config/toyama-transit.json) に明示する。新規フィードは、カタログから発見しても、再配布、表示、加工・商用利用の条件を一次資料で照合してから追加する。
- [取り込みスクリプト](../scripts/prepare-transit.py) は、GTFS ZIPのハッシュ、期間、停留所・便数と差分をJSONで出す。必須表、ID参照、運行日、乗降可否、時刻の順序、歩行行列と停留所の対応を検証する。未知の乗り換え規則や頻度運行、対象日を含まないフィードはエラーとして止める。
- AIには公開カタログの比較、ライセンス確認の候補箇所、JSON差分の要約、回帰テスト候補の提示を任せる。この改修でも、公開資料とZIPを照合し、路面電車の `route_type` の不一致や運賃表の欠落を確認した。時刻・運賃と徒歩経路は公表データから決定的に計算する。欠落はAIで補完しない。新規の権利判断、ダイヤ・候補の目視確認、公開は担当者が行う。利用者の位置や検索履歴は外部AIに渡さない。
- 運用ではカタログとフィードの変更を日次で確認し、ダイヤ改正を検出する。ライセンスと期限を再確認し、検証と既知経路の回帰テストを通したスナップショットだけを配信する。未承認・期限切れのデータを表示しない。前回検証済み版の保存、切り戻し、更新失敗時の通知を運用に含める。

### 再生成の手順

1. Python 3で `scripts/prepare-transit.py --inputs /tmp/tsugi-transit --download --fetch-foot --walk-cache /tmp/tsugi-walking.json --as-of YYYY-MM-DD` を実行し、JSONを確認する。公開歩行サービスは収録点が増えた場合に使い続けず、自前の歩行グラフから互換行列を作る。既存の行列が使えるときは `--fetch-foot` を省く。
2. `--compare /tmp/previous-report.json` を指定して、フィードのハッシュ、バージョン、期間、停止点、便数の差分を確認する。変更内容を確認した上で `--write` を付け、ブラウザー用スナップショットを生成する。
3. `npm test` で実ダイヤの乗り換え、徒歩の上限と上限1秒超過、休止日、期限切れを確認する。期待する便が実際の時刻表や公式の案内と合うかを確認してからプレビューへ反映する。

## OpenTripPlanner での照合

Java 21で動く OpenTripPlanner 2.7.0をローカルで起動し、承認済み2本のGTFSで `java -Xmx768m -jar otp-shaded-2.7.0.jar --build --save <フィード用ディレクトリー>` を実行した。路面電車のZIPは検証用コピーで `routes.txt` の `route_type` を `0` に正規化した。109停留所、両フィード計765便を読み込めた。警告は低速区間9件と乗継用の接続がない停留所1件だった。この照合では道路グラフの構築を含めていない。実際のプレビューで使う徒歩連携は、先に取得したOSMの歩行経路と時刻表を用いてブラウザー上で検証した。

広域版でOTPを使うときは、地域のOSM PBFを入力し、ビルドと検索に使う Java・OTP の版を固定する。直線距離で生成された乗継は受け入れず、経路の歩行区間と時間を既知の例で照合する。現行の富山版にOTPサーバーの接続は不要。[OTP 2.7の構築手順](https://docs.opentripplanner.org/en/v2.7.0/Basic-Tutorial/)

## 全国対応と必要になる協力

地名・停留所は `地域/フィード/元ID` を基準にし、同名でも別として管理する。同じ駅・近いバス停は座標だけで同一扱いせず、歩行ネットワークと提供元の乗換規則を検証する。地域ごとに有効なデータ範囲と期間を返し、経路が見つからない場合とデータ未対応を区別する。収録が増えたら経路APIに、出発・到着・歩行秒数・乗降の出典を揃え、地域グラフを自前のOTPサーバーに移せるようにする。OTPの徒歩を少なくする優先設定だけに頼らず、全徒歩区間をサービス側で足して上限を検査する。地域間を結ぶ便や更新時刻にはそれぞれの情報源と許諾を添える。

今回の富山版は、アカウント登録、新規APIキー、新規サーバーを必要としない。ODPTのキーが必要なデータを採用するときは、オーナーが[開発者サイト](https://developer.odpt.org/)で規約を確認し、プロジェクト用のアカウントを登録してキー発行を受ける。キーはサーバー側の環境変数に登録する。公開の条件が不足するフィードは、再配布・商用表示・保存・更新の許可を提供元に申請する。常時稼働するOTPの導入前に、Java実行環境、必要メモリ、ストレージ、配信量、月額の見積もりを示して承認を得る。
