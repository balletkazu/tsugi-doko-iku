# アプリ内乗換検索の比較と開発計画

2026年11月25日の公開資料をもとに比較した。富山市では収録した時刻表から、バス1便と徒歩の経路・時刻・運賃を検索する。[試作と出典](toyama-pilot.md) その他の地域では入力条件の確認を提供し、利用者が選択すると Google マップを別タブで開く。

|---|---|---|---|
| Google Maps Platform Routes API | 乗換、徒歩区間、提供可能な運賃を単一レスポンスで表示できる。モード・地域によって対象が異なり、ローカルバスや離島航路は実データで確認が必要。往路・復路も個別に検証する。 | 公開仕様の `LESS_WALKING` は優先指定。30・60・120分の厳密な検索条件は公開仕様で確認できない。返却された徒歩区間を合算して上限外を除けるが、返却されなかった候補は拾えない。 | 従量課金、請求アカウントとキーが必要。Compute Routes の公開料金例は Essentials が月1万件の無料枠と次の帯で1,000件あたり5米ドル、Pro が月5,000件と1,000件あたり10米ドル。使用機能で SKU が変わる。地点検索・地図は別 SKU。帰属表示、Google 地図での表示、保存や再配布の制限があり、栞に経路を保存する前に確認する。 |

## 検索の設計と受け入れ条件

1. **最初の検証は許諾を確認した一地域で実施する。** 都市の鉄道とバスだけでなく、最寄りの停留所から30分以上歩く旅先、乗継と歩行を含む旅先、可能ならローカルバスや船を含む経路を検証用に選ぶ。フィードごとに更新日、収録便、利用条件、欠落、配信元を台帳に記録する。OTP はローカル検証から始め、ホスティングが必要な時点で費用を算定する。
2. **徒歩上限は候補の合計時間に適用する。** 30・60・120分を、歩きと確定できる各区間の秒数の合計として定義する。乗車や待ち時間は含めない。可能な提供元では検索パラメータにも渡し、結果表示前に全徒歩区間を検査する。徒歩時間が欠落する候補は「条件を確認できない」と区別し、上限を満たす結果には入れない。上限ちょうど、1秒超過、アクセス＋乗換＋イグレスの合計、長い徒歩が必要な地点、運行終了をテストする。徒歩上限を緩和する場合は利用者が選ぶ。
3. **結果をアプリ内に表示する。** サーバーの `RouteProvider` が地点・出発日時・上限・優先条件を受け取り、区間ごとの手段・時刻・所要時間・徒歩合計・運賃の提供有無、出典、取得日時を返す。画面は接続なし、対応地域外、候補なし、障害を区別する。外部 API のキーはサーバー側のみで保持する。正確な座標は必要なときにだけ要求し、永続ログに既定で含めない。
4. **順位の根拠を表示する。** 「最短」は到着までの時間、「格安」は運賃が全区間で確認できた候補で比較する。「景色」は出典のある展望地点・歩行区間、「寄り道」は候補経路の形状と立ち寄った場合の追加時間を使う。許諾または必要データが揃わないモードは画面で未提供とする。
5. **費用・範囲・運用を比較して採用する。** 駅すぱあと・ジョルダンには利用量、地域、2時間までの徒歩候補、経路の保存・共有条件を揃えて問い合わせる。Google はリクエスト数と地図・地点検索を別で試算する。OTP はサーバー、フィード更新、運行情報の監視を含めて試算する。有料サービスへの登録・契約は費用と代替を示して承認を得る。
